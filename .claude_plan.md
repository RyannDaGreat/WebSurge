## 1. Piano roll editors

### The candidates

| Project | Shape | Verdict |
| --- | --- | --- |
| [webaudio-pianoroll](https://github.com/g200kg/webaudio-pianoroll) | single-file custom element; **makes no sound**, emits note events to a callback | **best fit** |
| [signal](https://github.com/ryohey/signal) | full React sequencer app: multi-track, velocity lanes, MIDI I/O | fork territory |
| [pixi-piano-roll](https://github.com/mmatuscak/pixi-piano-roll) | PixiJS component | stale (~2024) |
| [WaveRoll](https://arxiv.org/abs/2511.09562) | comparative MIDI visualisation | view-only, wrong tool |

`webaudio-pianoroll` is the right shape precisely *because* it refuses to make
sound. It hands you note events and expects something else to be the
instrument — which is exactly the seam we have. Its sequence is a plain array on
the element, and it exposes grid/drag edit modes, rubber-band select, and
edge-drag resize.

### The actual work is NOT the piano roll

It is **timing**. Our worklet applies note events the moment the message
arrives:

```js
case 'noteOn': sh.noteOn(msg.channel, msg.key, msg.velocity); break;
```

No timestamp. Fine for a computer keyboard, useless for a sequencer — every note
would land on a `postMessage` boundary, jittering by up to a render quantum.

What is needed:

1. **Timestamped event queue in the worklet.** Messages carry a target sample
   position; `process()` drains events due within the current 128-frame block
   and applies them at the right offset. Surge's own block is 32 frames, so we
   already sub-divide — events can land on a 32-frame boundary cheaply, or
   exactly if we split blocks.
2. **A scheduler on the main thread** that looks ahead ~100 ms and posts events
   with absolute sample times, the standard Web Audio lookahead pattern.
3. **Transport ↔ tempo.** We now have `sh_set_tempo()` from the delay fix. A
   sequencer would drive it, which means Surge's temposynced delays and LFOs
   would lock to the sequencer's grid — that is a real payoff, not a side effect.

Estimate: the piano roll integration is small; the scheduling is the day of work.

## 2. GitHub Pages — yes, comfortably, with one decision

### Measured footprint

```
src total                497 MB
largest single file      < 20 MB   (surge-gui.wasm is 19 MB)
cold load per visitor    26 MB     (gui wasm + engine wasm + js + patch index)
factory patches only     24 MB
factory wavetables       6.3 MB
```

### Against the limits

| Limit | Ours | Verdict |
| --- | --- | --- |
| 100 MB hard per-file push | max ~19 MB | **fine** |
| 1 GB published site (soft) | 497 MB | fits, but eats half the budget |
| ~1 GB repo (soft) | currently 8 MB; +497 MB if data is committed | **the real friction** |
| 100 GB/month bandwidth (soft) | 26 MB cold load → ~3,800 visits/mo | fine personally |
| Custom response headers | **not supported** | see below |
| HTTPS | free and automatic | **a genuine win** |

**HTTPS for free matters more than it sounds.** AudioWorklet needs a secure
context — the bug that broke LAN access. On Pages that requirement just
evaporates.

**The friction is git, not Pages.** `src/data/` is currently gitignored and
regenerated by `tools/stage_data.sh` from the pinned Surge SHA. Deploying to
Pages means committing ~497 MB of binary assets, which bloats the repo
permanently (git history keeps every version).

### Three ways to handle the data

1. **Factory only.** ~30 MB of data, whole site ~56 MB. Comfortable, fast, and
   covers the 639 patches most people would ever touch. Loses the 2,920
   third-party ones.
2. **Everything, committed.** ~500 MB repo. Works, but the repo becomes
   unpleasant to clone and sits near the soft limits.
3. **Split: site on Pages, data in GitHub Releases.** Release assets allow up to
   2 GB each and do **not** count against the Pages 1 GB limit. Fetch patches
   from release URLs on demand. *Needs verifying:* whether release-asset
   redirects to `objects.githubusercontent.com` send permissive CORS headers.
   If they do, this is the best of both.

My preference: **(1) now, (3) if the full library is wanted.**

### The one real blocker, and it is in the future

GitHub Pages **cannot set custom headers** — a request open since 2022 with no
ETA. That means no `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`,
so **no `SharedArrayBuffer`**.

Irrelevant today: we are single-threaded with two separate engine instances.
It directly blocks the **unification plan**, which depends on a shared heap
between the main thread and the AudioWorklet.

Workaround exists: `coi-serviceworker` registers a service worker that injects
the headers, and browsers honour them from a service worker. Caveats worth
knowing before relying on it — it forces a reload on first visit, and it
conflicts with any other service worker the app registers.

Alternative if that becomes annoying: Netlify or Cloudflare Pages, both of which
take a `_headers` file and set COOP/COEP properly. Same static site, no code
change.

### Licensing

Surge XT is GPLv3, so a published build must carry its source offer. The repo
*is* the source, so this is satisfied by linking it — but the site needs a
visible LICENSE and attribution, which it currently lacks.

## Suggested order

1. Mount `/SurgeXTData` — unblocks the jog buttons, Surge's own patch browser,
   and wavetable patches in one change.
2. Ship to Pages, factory patches only. Cheap, and HTTPS comes free.
3. Sequencer: timestamped event queue in the worklet, then
   `webaudio-pianoroll` on top, driving `sh_set_tempo`.
4. Unify the two engine instances — and note this is the step that forces the
   `coi-serviceworker` decision, or a move off Pages.
